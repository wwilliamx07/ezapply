# Security and privacy

ezapply handles personal data, drives a browser, and reads source code. Its threat model is a single user
on their own machine, facing hostile **content** (postings, forms, web pages), and other **software**
(websites, other local processes) trying to use its capabilities.

## Threats and controls

| Threat | Controls |
|---|---|
| **A web page calls the companion** (CSRF, DNS rebinding) | Binds to `127.0.0.1` only. Every HTTP request must name the bound loopback host (`Host` check). `/mcp` requires the bearer token and refuses any request with an `Origin` header, which browsers always send cross-site. GitHub pages need one-time, 30-minute state values; the login start needs a nonce issued to Claude; the POST routes need a secret from their page: the existing-app form its state; the review and onboarding pages their token, which the first load trades for an `HttpOnly`, `SameSite=Strict` cookie on the page's own path (and takes off the address bar), and every POST of theirs must also carry `Origin` equal to the companion's own address, so no other site can act even with the token ([ui](components/ui.md#how-a-page-talks-to-the-companion)) |
| **An existing app's client secret leaking** | The user enters it on the companion's own page, never in chat, so it isn't in any transcript. It stays in memory until a login with it succeeds, then goes to the keychain; a failed login stores nothing. The page's CSP lets forms post only to the companion itself and GitHub |
| **A web page or local program impersonates the extension** | WebSocket upgrades must come from an extension origin (`chrome-extension://…`); after pairing, only the pinned id. The `hello` must carry the pairing code, or arrive while a pairing window is open. Only `extension_pair` opens a window, so it takes an MCP session (there are no control routes). A window closes after one pairing |
| **Prompt injection in a posting, form or repo** | Postings are captured twice: raw, and visible-only. `posting.md` is built from the visible copy, so hidden text never reaches the default context. `EZAPPLY.md` names the sources (postings, forms, `repo-cache/` files, library documents, example letters), describes what injections look like, and says to never act on them and to tell the user; the MCP instructions repeat it for sessions and subagents without `CLAUDE.md`, and the `ezapply-apply` and `ezapply-index-repo` skills restate it. A posting's application requirements are honoured only when they concern what a human applicant submits; anything aimed at an AI, hidden, or unusual is treated as an injection. The tool set can't click arbitrary elements, run scripts, navigate, or submit, which bounds what a successful injection could do |
| **Attaching what the user didn't see** | In the default `after-approval` attach mode, `upload_file` refuses a generated document unless the user approved that exact version (SHA-256) on the review page. No tool approves, and approval in chat doesn't count, so an injection can't approve either. The review page and its PDFs need a random token in the URL (compared in constant time), are served only to the loopback host, can't be framed, run only the UI package's scripts from the companion (no inline script), load nothing from elsewhere (no CDN, no web fonts), and send requests only to the companion itself. The bytes served are those read when the review opened, and their hash is what an approval records |
| **Submitting without the user** | No submit or general click tool. `go_next` refuses on review and on submit controls (on a one-page application, Oracle's single page and every Greenhouse, Lever and Ashby application, Submit is the only way on, so it always refuses). No adapter call touches a submit control. The page-level submit guard (in the adapter engine, so on every site, with the site's own submit test) cancels untrusted click/pointer/key/submit events aimed at a submit control; a conformance test checks, for every registered site, that it blocks a synthetic click and Enter on that site's Submit. Real clicks are trusted and always work. There's no generic definition for unknown sites: a site's submit test is written from its own pages, never guessed ([adapters](components/adapters.md#never-submitting)) |
| **Changing or running the user's code** | The GitHub App has only `contents: read` and `metadata: read`. Repos are mirrored into `repo-cache/`, never the user's working copies. Files are read-only after every sync. Claude Code settings deny Edit/Write/NotebookEdit there. Skills forbid building, installing or running anything from it. `repo_diff` runs git with hooks and every transport off and with `--no-ext-diff --no-textconv`, so the repo's `.gitattributes` can't make it run a diff driver |
| **Malicious repo content attacking git** | HTTPS-only transports (no `file://`, ssh, `ext::`), symlinks off, hooks off, credential helpers off, no prompts. The token is passed per command and never written to `.git/config`. The workspace check's `ls-remote` goes through the same hardening |
| **Other local users reading the GitHub token** | git gets it through `GIT_CONFIG_*` environment variables, not its command line: a process's arguments are readable by other users on Linux (`/proc/<pid>/cmdline`), its environment isn't |
| **Malicious TeX from posting text** | Shell escape is always disabled for every engine; a `% !TEX program` comment can only pick from a fixed list of engine names and is never passed to a process, and option-style comments (`% !TEX options`, `program = pdflatex --shell-escape`) are refused or ignored; builds time out and are killed with their process tree; TeX sources must be under `postings/` or `templates/` |
| **Reading or writing outside the workspace** | Every path from Claude is resolved and checked against the folders each operation allows. Uploads only from `postings/` and `library/` (≤25 MB). Template and example imports copy from outside, never link. The workspace check reads (never writes) the folder a template was imported from, a path the user gave at import. Deleting a deselected repo's knowledge and cache takes `workspace_change_mark`, which the skill calls only after asking. A template's `main` must stay inside `templates/<kind>/`, and posting ids must be plain folder names, so `../x` can't reach outside `postings/` |
| **Something handed to a browser or the OS opener** | `open_file` opens only paths from the allowed folders; `github_login`, `review_documents` and `onboarding` open only `http://127.0.0.1:<port>/` URLs (anything else is refused before it reaches a program). Neither goes through a shell. A file goes to the user's browser only if it's a PDF, image or text file: a posting's captured `.html` or an `.svg` could run script in a tab of the browser that holds the user's sessions, so they go to their default application. Files reach the browser as `file://` URLs, which can't be read as a command-line flag. The browser's program comes only from the App Paths registry key or the usual install folders (Windows), `/Applications` (macOS) or PATH; the extension reports only a name from a fixed list |
| **Filling or marking the wrong application** | Form activity is credited to the active posting only when the tab may be its application: the same job, the tab bound to it, its tenant (Workday tenant, Oracle host and site number, Greenhouse board, Lever company, Ashby organization, Phenom careers host, Dayforce client, SuccessFactors company) or its job title, and nothing tying the tab to another posting. Otherwise nothing that changes the page runs, nothing is logged or moved, and Claude is told (`postingMismatch`, `posting_mismatch`). A posting with nothing to compare binds the tab on its first change, so a second posting can't take it; Claude tells the user which posting it was bound to. Only `posting_activate { id, tabId }`, when the user says so, rebinds a tab. The default tab is the best match ([which posting](mcp-tools.md#forms)) |
| **The extension being made to talk to other servers** | The manifest's policy for extension pages: they may only connect to `ws://127.0.0.1:*` (`connect-src`), and run scripts only from the extension (`script-src 'self'`) |
| **The extension reading or acting on pages it has no business with** | The extension holds every site (`<all_urls>`) and the `debugger` permission, so it can tell a form site by its pages' bodies on whatever host (Phenom and Oracle run on employers' own domains), and a form call isn't stuck on a host nobody granted ([why](components/sites.md#the-registry)); Chrome warns "Read and change all your data on all websites" at install. What it does with that is bounded: only the paired companion (pinned extension id, pairing code) can ask it anything, and the companion only on a call from Claude (bearer token). On every tab and frame `browser.status` runs one function in the isolated world that only tests the registry's selectors and returns the site's id and the page's URL, never content ([telling a page's site](components/extension.md#telling-a-pages-site-framests)). A page's content is read only by Capture (the user's click) and by the form tools, whose adapter is injected only into a page that shows a form site, and never submits ([never submitting](components/adapters.md#never-submitting)). `webNavigation` lists every tab's frames' URLs (beside the tab URLs `tabs` already gives); only frames on a form site are sent. Where the user limits the access (Chrome's site access), the extension asks for it again only through the browser's own prompt: in the Capture click, or from a window a form call opens (an extension page web pages can't open), or the options page. The debugger is attached only to the application tab of a form call (`tab.show`), sends only focus emulation and, for a screenshot, `Page.captureScreenshot`, and detaches when the fill goes idle or the companion disconnects; Chrome's bar shows the whole time it's attached (Cancel on it detaches until the next form call) ([focus emulation](components/extension.md#focus-emulation-emulationts)) |
| **A forged session header** | The session header on `/mcp` (`x-ezapply-session`) is read only on a request that already carries the bearer token. It says which panel conversation a call comes from, so a forged one could at most put a question card in another conversation, where the user answers or dismisses it |
| **The port open when ezapply isn't in use** | There is no background process: the companion listens only while `ezapply` runs in a terminal, and closes its port when that stops (Ctrl+C, or the terminal closing). Nothing else starts it; the relay answers "not running" instead of starting anything |
| **Something other than the user approving a command or answering for them** | Under `ezapply`, Claude Code's permission prompts and questions go to the side panel ([agent](components/agent.md#cards-needsts)). The panel is an extension page that reaches the companion only through the paired extension (pinned id, pairing code): the companion takes `panel.*` from that connection only, so a web page or a token from another page can't answer a card. An approval answers only a request the agent raised and that's still open; it's never remembered (the workspace's permission rules are the only standing approvals), and no answer in 10 minutes is a deny. The agent runs in Claude Code's Auto mode by default (the user's choice): its classifier, not a card, decides most actions, which is the guard against a command injected through a posting; **Ask first** puts every command and edit the workspace's rules don't allow on a card. Not offered: a mode that skips the checks (`bypassPermissions`), since postings are untrusted. The card shows the command or the file and the change whole. The relay only passes on `panel.*` methods, so the panel can't call the form methods. What the panel shows of posting text, the agent's words and a form's labels is text, never HTML (the agent's Markdown is built as elements). Chrome's `sidePanel` permission adds no install warning |
| **Secrets leaking** | GitHub secrets live in the OS keychain. `config.json` is mode 0600. `.mcp.json` holds no token. Logs redact page content, form values, tokens and authorization headers |
| **Debug records spreading personal data** | Debug mode is off by default, and `get_form` says `debug: true` while it's on. Its records (`debug/` in the workspace) hold filled values, full adapter results, the adapter's trace, and with `debug.markup` the pages with their values and screenshots of failed steps. They stay on disk and are never sent anywhere. The trace and markup come back beside the bridge's result, never in it (`WithDebug`), so they can't reach a tool result or the conversation; a password input's value is never saved, a request's query and body never recorded, and an upload's file contents are left out. The workspace agent is denied reads of `debug/**`. `debug.maxMB` caps the folder, and `ezapply debug clean` deletes it. `ezapply debug export` blanks the values and replaces the profile's strings, the tenant and the job title, but writes only beside the source, for the user to check before anything goes into the repo: the scrub can miss what the page shows differently |
| **Debug mode changing the page it watches** | The trace's hooks (the DOM query methods, `fetch` and XHR, `console.error`, error listeners, a mutation observer, and getters on the adapter's own waits) are installed only for a debugged call, in the page's MAIN world where the adapter already runs, and taken off when it ends; each is restored only if the page hasn't replaced it since, and a trace never taken comes off after 15 minutes. They only record: no call, event or request is changed or blocked. Without debug nothing is installed. Page-made strings (labels, error messages) in a record are data from the employer's page: Claude working on ezapply reads them as such, never as instructions |
| **The onboarding page writing the user's files** | Only with the page's cookie and from the companion's own origin. It writes only `profile/profile.yaml` (the keys the schema models, in place, and only a result that validates), `profile/answers.yaml` (an entry's `answer`), `profile/preferences.md`, the attach mode in `ezapply.config.json`, `profile/repos.yaml`, and new files in `library/` (the name only, a fixed list of types, 25 MB, never over another file). It imports templates through `template_import`'s own checks (never from the workspace outside `library/`, never from a scratchpad). The PDFs it serves are under `templates/` only. **It runs no command:** installing TeX is a task for Claude, run in the terminal where the user approves it; a page that could start installers would widen what a stolen token could do. The OS's file dialog it opens runs no shell and gets its title from the environment or as an argument, never as script ([ui](components/ui.md#writing-the-users-files)) |
| **Personal data leaving the machine** | Nothing is sent anywhere except the GitHub API (repo metadata and contents) and what the user puts into an application. A future decision provider would get only the slice each question needs |
| **Filling what the user didn't approve** | Passwords are never filled. Oracle's email step (email, terms, emailed code) is the user's: `go_next` refuses there, and its hidden honeypot field is never offered. EEO answers come only from the profile, verbatim, or from what the user sends. Sensitive, unanswered, EEO and salary questions are asked, on a card in the side panel (or in chat without one): the agent may suggest an answer, flagged as sensitive with where it came from, but nothing is filled until the user answers. Every fill is logged with its source, and the hand-off lists every answer from the user or Claude's judgment for a second look. Nothing is filled without the model: deterministic autofill was removed ([status](status.md#deterministic-autofill-removed)) |

## Accepted limits
- Anything running as the user can read `~/.ezapply/config.json` and so reach the companion while a chat
  runs. That's the same trust boundary as the user's other files; the pairing code and MCP token protect
  against the browser and other users, not against the user's own malware.
- The companion carries on after an uncaught exception (it logs it) rather than ending the chat. Node warns
  that state may be inconsistent after one; every error the companion expects is handled per request, so an
  uncaught one is a bug, and losing Claude's tools and terminal mid-application is the worse outcome.
- Code-less pairing (an open pairing window admits an extension that sends an empty code) is no weaker
  than typing the code: the code was always readable from that same `config.json`, and opening a window
  needs an MCP session, which needs the MCP token from it. The window admits one extension and closes, and
  extension-id pinning still applies, so it never admits a second one.
- The site adapters run in the page's own JavaScript context, so the page could in principle observe
  or tamper with them. It holds no secrets there: it gets only the values it's asked to fill.
