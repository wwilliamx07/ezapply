# Security and privacy

ezapply handles personal data, drives a browser, and reads source code. Its threat model is a single user
on their own machine, facing hostile **content** (postings, forms, web pages), and other **software**
(websites, other local processes) trying to use its capabilities.

## Threats and controls

| Threat | Controls |
|---|---|
| **A web page calls the companion** (CSRF, DNS rebinding) | Binds to `127.0.0.1` only. Every HTTP request must name the bound loopback host (`Host` check). `/mcp` requires the bearer token and refuses any request with an `Origin` header, which browsers always send cross-site. GitHub pages need one-time, 30-minute state values; the login start needs a nonce issued to Claude; the POST routes need a secret from their page: the existing-app form its state, a review answer the review's token, neither readable by another site |
| **An existing app's client secret leaking** | The user enters it on the companion's own page, never in chat, so it isn't in any transcript. It stays in memory until a login with it succeeds, then goes to the keychain; a failed login stores nothing. The page's CSP lets forms post only to the companion itself and GitHub |
| **A web page or local program impersonates the extension** | WebSocket upgrades must come from an extension origin (`chrome-extension://…` or `moz-extension://…`); after pairing, only the pinned id. The `hello` must carry the pairing code, or arrive while a pairing window is open. Only `extension_pair` opens a window, so it takes an MCP session (there are no control routes). A window closes after one pairing |
| **Prompt injection in a posting, form or repo** | Postings are captured twice: raw, and visible-only. `posting.md` is built from the visible copy, so hidden text never reaches the default context. `EZAPPLY.md` names the sources (postings, forms, `repo-cache/` files, library documents, example letters), describes what injections look like, and says to never act on them and to tell the user; the MCP instructions repeat it for sessions and subagents without `CLAUDE.md`, and the `ezapply-apply` and `ezapply-index-repo` skills restate it. A posting's application requirements are honoured only when they concern what a human applicant submits; anything aimed at an AI, hidden, or unusual is treated as an injection. The tool set can't click arbitrary elements, run scripts, navigate, or submit, which bounds what a successful injection could do |
| **Attaching what the user didn't see** | In the default `after-approval` attach mode, `upload_file` refuses a generated document unless the user approved that exact version (SHA-256) on the review page. No tool approves, and approval in chat doesn't count, so an injection can't approve either. The review page and its PDFs need a random token in the URL (compared in constant time), are served only to the loopback host, can't be framed by other origins, run only their own script (by nonce), and send forms and requests only to the companion itself |
| **Submitting without the user** | No submit or general click tool. `go_next` refuses on review and on submit controls (on a one-page application, Oracle's single page and every Greenhouse, Lever and Ashby application, Submit is the only way on, so it always refuses). No adapter call touches a submit control. The page-level submit guard (in the adapter engine, so on every site, with the site's own submit test) cancels untrusted click/pointer/key/submit events aimed at a submit control; a conformance test checks, for every registered site, that it blocks a synthetic click and Enter on that site's Submit. Real clicks are trusted and always work. There's no generic definition for unknown sites: a site's submit test is written from its own pages, never guessed ([adapters](components/adapters.md#never-submitting)) |
| **Changing or running the user's code** | The GitHub App has only `contents: read` and `metadata: read`. Repos are mirrored into `repo-cache/`, never the user's working copies. Files are read-only after every sync. Claude Code settings deny Edit/Write/NotebookEdit there. Skills forbid building, installing or running anything from it |
| **Malicious repo content attacking git** | HTTPS-only transports (no `file://`, ssh, `ext::`), symlinks off, hooks off, credential helpers off, no prompts. The token is passed per command and never written to `.git/config`. The workspace check's `ls-remote` goes through the same hardening |
| **Other local users reading the GitHub token** | git gets it through `GIT_CONFIG_*` environment variables, not its command line: a process's arguments are readable by other users on Linux (`/proc/<pid>/cmdline`), its environment isn't |
| **Malicious TeX from posting text** | Shell escape is always disabled for every engine; a `% !TEX program` comment can only pick from a fixed list of engine names and is never passed to a process, and option-style comments (`% !TEX options`, `program = pdflatex --shell-escape`) are refused or ignored; builds time out and are killed with their process tree; TeX sources must be under `postings/` or `templates/` |
| **Reading or writing outside the workspace** | Every path from Claude is resolved and checked against the folders each operation allows. Uploads only from `postings/` and `library/` (≤25 MB). Template and example imports copy from outside, never link. The workspace check reads (never writes) the folder a template was imported from, a path the user gave at import. Deleting a deselected repo's knowledge and cache takes `workspace_change_mark`, which the skill calls only after asking. A template's `main` must stay inside `templates/<kind>/`, and posting ids must be plain folder names, so `../x` can't reach outside `postings/` |
| **Something handed to a browser or the OS opener** | `open_file` opens only paths from the allowed folders; `github_login` and `review_documents` open only `http://127.0.0.1:<port>/` URLs (anything else is refused before it reaches a program). Neither goes through a shell. A file goes to the user's browser only if it's a PDF, image or text file: a posting's captured `.html` or an `.svg` could run script in a tab of the browser that holds the user's sessions, so they go to their default application. Files reach the browser as `file://` URLs, which can't be read as a command-line flag. The browser's program comes only from the App Paths registry key or the usual install folders (Windows), `/Applications` (macOS) or PATH; the extension reports only a name from a fixed list |
| **Filling or marking the wrong application** | Form activity is credited to the active posting only when the tab may be its application: the same job, the tab bound to it, its tenant (Workday tenant, Oracle host and site number, Greenhouse board, Lever company, Ashby organization) or its job title, and nothing tying the tab to another posting. Otherwise nothing that changes the page runs, nothing is logged or moved, and Claude is told (`postingMismatch`, `posting_mismatch`). A posting with nothing to compare binds the tab on its first change, so a second posting can't take it; Claude tells the user which posting it was bound to. Only `posting_activate { id, tabId }`, when the user says so, rebinds a tab. The default tab is the best match ([which posting](mcp-tools.md#forms)) |
| **The extension being made to talk to other servers** | Firefox build: extension pages may only connect to `ws://127.0.0.1:*` (`connect-src`), and scripts only from the extension (`script-src 'self'`) |
| **The extension reaching more sites than it needs** | Host permissions only for Workday's candidate sites (`*.myworkdayjobs.com`, `*.myworkdaysite.com`); not Workday's marketing site or employee tenants. Oracle career sites can be on any host, so the manifest only declares `https://*/*` as optional and the extension holds just the origins the user granted, one at a time, by Set posting on that site or the options page ([why not `*.oraclecloud.com`](components/oracle-adapter.md#site-access)); Greenhouse, Lever and Ashby are granted the same way rather than listed in the manifest, so the install asks for nothing the user may never use ([registry](components/protocol.md#the-site-registry-sitests)); a form call on another origin fails before injecting anything. Capture uses the click's `activeTab` grant, which doesn't extend to other sites' frames (an unreadable embedded board is opened in its own tab instead) |
| **Another local program steering `ezapply chat`** | The wrapper reads its session state in-process; nothing about it is served over HTTP. The session header on `/mcp` (which needs the bearer token) only feeds the per-session call counts; a forged one could at most make the wrapper restart (or not restart) its own Claude, which the user started and can `claude --resume`. The wrapper ends only the Claude it started |
| **The port open when ezapply isn't in use** | There is no background process: the companion listens only while an `ezapply chat` is open, and closes its port when Claude exits. Nothing but a chat starts it; the relay answers "not running" instead of starting anything |
| **Secrets leaking** | GitHub secrets live in the OS keychain. `config.json` is mode 0600. `.mcp.json` holds no token. Logs redact page content, form values, tokens and authorization headers |
| **Debug records spreading personal data** | Autofill debug mode is off by default, and `get_form` and `autofill_step` say `debug: true` while it's on. Its records (`debug/` in the workspace) hold filled values and full adapter results. They stay on disk and are never sent anywhere. An upload's file contents are left out. The workspace agent is denied reads of `debug/**`. `debug.maxMB` caps the folder, and `ezapply debug clean` deletes it |
| **Personal data leaving the machine** | Nothing is sent anywhere except the GitHub API (repo metadata and contents) and what the user puts into an application. A future decision provider would get only the slice each question needs |
| **Filling what the user didn't approve** | Passwords are never filled. Oracle's email step (email, terms, emailed code) is the user's: `go_next` refuses there, and its hidden honeypot field is never offered. EEO answers come only from the profile, verbatim. Sensitive, unanswered, EEO and salary questions are asked in chat. Every fill is logged with its source. `autofill_step` fills only values from the profile and the answer bank: never a sensitive or unanswered entry, an EEO value the profile doesn't hold, a reversed wording, a password, a file or a read-only field; options by a strict match (a city or postal code by the adapter's own match, with what the field then shows checked); and every automatic fill is in its result and listed at the hand-off. Form text only decides which field a value goes into (exact wording, or a fixed label pattern within a row), never what the value is ([autofill](components/autofill.md)) |

## Accepted limits
- Anything running as the user can read `~/.ezapply/config.json` and so reach the companion while a chat
  runs. That's the same trust boundary as the user's other files; the pairing code and MCP token protect
  against the browser and other users, not against the user's own malware.
- The companion carries on after an uncaught exception (it logs it) rather than ending the chat. Node warns
  that state may be inconsistent after one; every error the companion expects is handled per request, so an
  uncaught one is a bug, and losing Claude's tools and terminal mid-application is the worse outcome.
- Code-less pairing (an open pairing window admits an extension that sends an empty code) is no weaker
  than typing the code: the code was always readable from that same `config.json`, and opening a window
  needs an MCP session, which needs the MCP token from it. The window admits one extension and closes, and
  extension-id pinning still applies, so it never admits a second one.
- Firefox temporary add-ons are unsigned; for permanent installs the add-on must be signed as unlisted.
- The site adapters run in the page's own JavaScript context, so the page could in principle observe
  or tamper with them. It holds no secrets there: it gets only the values it's asked to fill.
